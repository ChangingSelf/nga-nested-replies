# 存储机制分析：GM_setValue vs IndexedDB vs localStorage

## 当前使用：GM_setValue/GM_getValue

### 优点

1. **简单易用**：API简洁，直接存取
2. **跨域隔离**：每个脚本有独立的存储空间，不受同源策略限制
3. **自动持久化**：数据自动保存，无需手动管理
4. **跨浏览器**：Tampermonkey/Violentmonkey等脚本管理器都支持
5. **无需额外权限**：油猴脚本默认就有这个API

### 缺点

1. **容量限制**：通常限制在5-10MB（取决于浏览器和脚本管理器）
2. **同步API**：可能阻塞主线程（虽然数据量小时影响不大）
3. **无结构化查询**：只能通过key获取，不支持索引和查询
4. **无法枚举**：不能直接列出所有key（需要自己维护索引）

## 可选方案对比

### 1. IndexedDB

#### 优点

- **大容量**：通常几百MB到几GB，远超GM存储
- **异步API**：不阻塞主线程
- **结构化查询**：支持索引、范围查询、游标
- **事务支持**：保证数据一致性
- **性能优秀**：大量数据读写更快

#### 缺点

- **API复杂**：需要处理事务、对象存储、索引等概念
- **异步编程**：Promise/async-await增加代码复杂度
- **同源策略限制**：受域名限制，不同NGA域名可能无法共享
- **调试困难**：数据不如GM存储直观查看

### 2. localStorage

#### 优点

- **简单API**：类似GM_setValue
- **浏览器原生**：无需额外依赖
- **容量较大**：通常5-10MB

#### 缺点

- **同源策略限制**：不同域名无法共享数据
- **同步API**：可能阻塞主线程
- **容量不如IndexedDB**：只有几MB
- **无结构化查询**：和GM存储类似

## 性能对比

### 读写速度测试（理论值）

| 操作           | GM_setValue | IndexedDB    | localStorage |
| -------------- | ----------- | ------------ | ------------ |
| 小数据读(<1KB) | 极快        | 快           | 极快         |
| 小数据写(<1KB) | 极快        | 快           | 极快         |
| 大数据读(>1MB) | 慢          | 快           | 慢           |
| 大数据写(>1MB) | 慢          | 快           | 慢           |
| 批量查询       | 慢          | 快（有索引） | 慢           |

### 当前脚本的使用场景

我们的缓存数据特征：

- 单个帖子：通常0.5-20MB
- 元数据：几KB
- 页面内容：每页50-200KB
- 总缓存：配置限制50-200MB

## 建议和结论

### 短期建议：保持GM存储 ✅

**理由**：

1. **当前容量足够**：50MB限制可缓存10-25个中型帖子，对大多数用户足够
2. **无迁移成本**：已有代码稳定运行
3. **跨域优势**：支持多个NGA域名共享缓存
4. **用户无感知**：不需要请求额外权限

**优化措施**：

- ✅ 已实现容量限制和自动清理
- ✅ 已实现缓存索引优化查询
- ✅ 已实现缓存过期管理

### 中期考虑：混合存储方案

如果用户反馈容量不足，可以考虑：

**方案A：GM存储（元数据） + IndexedDB（大数据）**

```javascript
// 元数据用GM存储（小、需跨域）
GM_setValue('NGA_THREAD_META_xxx', metadata);

// 页面内容用IndexedDB（大、可异步）
await db.put('pages', { tid, page, content });
```

**优点**：

- 元数据跨域共享
- 大数据高效存储
- 混合优势

**缺点**：

- 代码复杂度增加
- 需要处理两套API
- IndexedDB受同源策略限制

### 长期规划：完全迁移到IndexedDB

**适用场景**：

- 用户需要缓存大量帖子（>50个）
- 单个帖子非常大（>50页）
- 需要复杂查询（如搜索、筛选）

**实施步骤**：

1. 创建IndexedDB封装层
2. 实现数据迁移工具
3. 保留GM存储作为备份
4. 逐步切换到IndexedDB

## 当前存储使用统计

### 数据结构

```javascript
// 配置（约1KB）
NGA_THREAD_CONFIG = {
    initialLoadPages: 5,
    preloadPages: 10,
    cacheExpireTime: 86400000,
    pageLoadInterval: 1000,
    maxCacheSize: 50MB
}

// 缓存索引（约1KB，10个帖子）
NGA_CACHE_INDEX = ['tid1', 'tid2', ...]

// 每个帖子元数据（约0.5-2KB）
NGA_THREAD_META_{tid} = {
    tid, title, totalPages, cachedPages,
    lastAccess, cacheTime
}

// 每个页面内容（约50-200KB）
NGA_PAGE_CONTENT_{tid}_{page} = {
    page, rawHTML, timestamp
}
```

### 容量估算

| 项目     | 大小  | 数量  | 总计      |
| -------- | ----- | ----- | --------- |
| 配置     | 1KB   | 1     | 1KB       |
| 索引     | 1KB   | 1     | 1KB       |
| 元数据   | 1KB   | 25帖  | 25KB      |
| 页面内容 | 100KB | 500页 | 50MB      |
| **总计** | -     | -     | **~50MB** |

## 性能优化建议

### 已实现的优化 ✅

1. 缓存索引：快速列举所有帖子
2. 容量限制：自动清理旧缓存
3. 分页存储：避免单个key过大
4. 延迟保存：批量操作减少写入次数

### 可以继续优化的点

1. **压缩存储**：使用LZ-string压缩HTML内容，可减少50-70%空间
2. **增量更新**：只缓存变化的部分
3. **懒加载**：按需读取，不一次性加载全部
4. **缓存预热**：后台预加载热门帖子

## 结论

**当前阶段不建议迁移到IndexedDB或localStorage**

理由：

1. GM存储对我们的使用场景完全够用
2. 跨域共享是重要需求（NGA有多个域名）
3. 代码简单稳定，无需增加复杂度
4. 50MB容量限制合理且可配置

**监控指标**：

- 如果用户普遍反馈容量不足
- 如果需要支持100+帖子缓存
- 如果需要复杂的缓存查询功能

**届时再考虑迁移到混合存储或完全IndexedDB方案。**
